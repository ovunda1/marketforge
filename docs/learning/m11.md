# M11: Dashboard

## What was built

A web dashboard, served by the compose stack, that anyone can use: a recruiter can watch
the market, place a practice order and read a backtest result in plain words; an engineer
can see the architecture, the measured numbers and the protocol underneath.

- **Four pages** (`dashboard/src/pages/`): Overview (architecture diagram, engine
  throughput and latency with workload and machine, test counts, the 1M-command
  differential test, the showcase result, every number read from results files), Live
  market (price ladder, trade tape, order entry, your account), Backtests (list, form, run
  page with equity curve, drawdown, cost breakdown and gross vs net) and How it works.
- **The market-data client in TypeScript** (`src/lib/bookClient.ts`), a port of
  `services/client.py`, and a feed around it (`src/lib/feeds.ts`) that resyncs on a gap or
  a new matcher epoch and measures the round trip with ping/pong.
- **Shared fixtures** that make the Python and TypeScript sides provably agree:
  market-data message sequences generated from a real matcher
  (`tests/fixtures/marketdata/`), decimal-to-ticks cases (`tests/fixtures/ticks/`) and
  backtest-form cases (`tests/fixtures/backtest_form/`), each run by pytest and by Vitest.
- **Gateway additions** (`services/api/app.py`): public reads (instruments, config,
  backtests, the data catalog), practice accounts in demo mode with a per-IP limit and a
  trusted-proxy client IP (`services/api/proxies.py`), the backtest form with server-side
  validation (`services/common/backtest_form.py`) and a per-account cap, `GET /orders`,
  `GET /fills`, `GET /accounts/me`, an OpenAPI security scheme, and integer safety
  (`services/common/safe_json.py`).
- **The data catalog** (`services/worker/catalog.py`): the worker describes its datasets
  (symbols, first and last dates, the trading calendar, never a price) in Redis.
- **Date and universe filters** for bar runs (`research/runs.py`, `[data] start/end/symbols`).
- **A demo liquidity bot** (`services/demo/bot.py`): a seeded quoter that trades the
  fictional symbols through the public API.
- **Deployment**: a `dashboard` image (Vite build, nginx), the bot, the worker's read-only
  data mount, fictional instruments (ACME, GLOBEX, INITECH, SMOKE).
- **M10 rough edges fixed**: `/docs` has an Authorize button (APIKeyHeader), and
  `make gateway-smoke` trades its own SMOKE symbol and cancels whatever it leaves open.
- **Tests**: Vitest (lib), pytest (gateway, fixtures, catalog, filters, bot, content,
  compose), Playwright end to end with axe, screenshots kept in CI.

## Design decisions

**React + TypeScript + Vite, served as static files by nginx.** The live page is a client
state machine (snapshot, deltas, resync, reconnect) plus a form with instant feedback;
that is what a component framework is for, and the state machine is plain TypeScript
tested without a browser. Server-rendered HTML (Jinja + HTMX) would have kept the repo
Python-only but put the protocol logic in the server or in untestable glue. nginx on the
same origin means no CORS and plain WebSocket proxying. Dependencies are few: React,
React Router, two self-hosted fonts; the charts are hand-written SVG.

**Share data, not code, between the two clients.** Python and TypeScript cannot share an
implementation, so they share expectations: a generator drives the real matcher through
scripted situations (in order, gap, stale after a snapshot, new epoch, resnapshot, before
any snapshot, levels moving through the window) and records the client state expected
after every message. Whenever the client is synced with the newest message, the generator
first checks that state against the engine's own depth, so the expectations rest on the
engine. A test regenerates the file and compares bytes, so a protocol change cannot leave
the fixtures (and one client) behind. The same pattern covers price parsing and the
backtest form's rules.

**Prices stay integer ticks in the browser.** A typed price is split into digits and
handled as `BigInt`: "1.15" at a 0.05 tick is 23 ticks exactly, where `1.15 / 0.05` in
floating point is 22.999999999999996. A price off the grid is an error that names the two
nearest valid prices, never a silent rounding. Formatting multiplies ticks by the tick's
digits and inserts the point as text, so it also prints money beyond 2^53.

**No integer is rounded silently, on either side.** The rule is: an integer the API
returns is either bounded far below 2^53 (per-order price and quantity are capped at the
gateway, so ids, prices and quantities are; counters grow by one per command) or a decimal
string (money aggregates, nanosecond timestamps, and any big integer in research output).
The gateway refuses to send anything else (500 `UNSAFE_INTEGER`), and the browser's parser
throws on any integer beyond 2^53 - 1. The guard paid for itself during development: trade
timestamps are nanoseconds since 1970, about 1.8e18, and the first `GET /trades` through
the dashboard came back as `UNSAFE_INTEGER` instead of quietly rounded times.

**Practice accounts, the client IP and who to believe.** "Try trading" creates an ordinary
trader account flagged `practice`, only in demo mode, limited per client IP. Behind nginx
every request comes from nginx's address, so the client IP must come from
`X-Forwarded-For`; but any client can send that header. nginx overwrites it with the
address it saw, the gateway believes it only when the TCP peer is a trusted proxy (the
`dashboard` service, resolved by name), and then only the last entry. uvicorn's own proxy
handling is off, so there is exactly one place where a forwarded address is believed.

**Keys in sessionStorage, never localStorage.** sessionStorage survives a reload but not
closing the tab, and other tabs cannot see it; localStorage would keep a working key on
disk indefinitely. A 401 forgets the key.

**Viewing is public, writing needs a key.** The market, backtest results and the catalog
are public reads; orders and backtests need an account. Backtest results were per account
in M10; they are derived, portfolio-level numbers (M9's guard), so making them public is
safe, and it is what "every run is recorded" requires. The gateway re-checks every metrics
payload with its own copy of the portfolio-level rule (a test keeps it in step with
research's), because it never imports the research stack.

**The backtest form is a separate, validated input.** Practice accounts may not send raw
configs (a config names file paths and can request long runs); they send a form that the
gateway validates against the worker's catalog and turns into a walk-forward config with
the showcase's costs. Allowed parameter values are small fixed sets with at most 12
combinations, so every run is short and reports honestly how many variations it tried.
Two runs at a time per practice account; an advisory lock per account makes the count and
the insert atomic.

**Honest results first.** A run page leads with one sentence that includes "not
statistically significant ... could well be luck" when the deflated Sharpe ratio is below
0.95, and every results page shows how many runs this server has made, failed ones
included.

**One design, chosen from screenshots.** Two directions (light and roomy, dark and dense)
were rendered as screenshots before building; the result is the dark, engineering one
with the light one's spacing and hierarchy. Tokens live in one stylesheet; every pair
passes AA (axe checks it); buy and sell carry an arrow and a word.

## Test strategy

- **Cross-language fixtures**: the same three JSON files run under pytest and Vitest.
- **Gateway behavior without services** (`test_dashboard_api.py`): fakes behind `Deps`,
  in-process ASGI: public reads, the IP trust (a spoofed header from a non-proxy is
  ignored; the proxy's own entry is used), the cap, the form, big integers as text and the
  `UNSAFE_INTEGER` refusal, the security scheme on keyed routes only, ping/pong.
- **Content checks** (`test_dashboard_content.py`): every engine reject reason, admin
  reject, cancel reason and gateway error code has a plain-language message and a fix,
  and nothing else does; the live instruments contain no real ticker.
- **Source rules** (Vitest): no `localStorage`, no float math in the price path, no
  `Response.json()`.
- **Compose tests**: the smoke run leaves no open orders; a spoofed header through nginx
  never reaches the limit's key; the catalog; the bot trades; security headers.
- **Browser tests** (Playwright, headless Chromium, never a local Chrome): the Overview
  against the files, the ladder against `GET /book` at the same `md_seq`, a matcher
  restart, trading end to end, rejects, keyboard-only trading, key storage, a backtest from
  form to result, the cap, axe on every page at two widths, the tour.

## Trade-offs and what was left out

- **No user accounts or login**: practice accounts are anonymous and never expire. A real
  deployment would need expiry and a sweeper; demo mode is meant for a local or
  short-lived stack.
- **Practice money is P&L from zero**: the engine has no cash balance, and inventing one in
  the UI would be a lie the risk gate does not enforce.
- **No price chart on Live market**: the ladder and tape are the exchange's own views; a
  candle chart would need a bar aggregation service.
- **Cancel only, no modify** in the UI, though the API supports cancel-replace.
- **The bot is simple**: a mean-reverting random walk with a static ladder; M12's demo adds
  a market maker and a momentum trader.
- **The Overview's numbers are fixed at build time**: rebuilding the image picks up new
  results; a live endpoint would add a moving part for numbers that change once a milestone.
- **One theme**, by choice.

## Interview questions

1. **How do you know the browser and the Python client apply market data the same way?**
   Both run the same fixture file, generated from a real matcher, with the expected state
   after every message; the generator checks those states against the engine's depth, and a
   test regenerates the file byte for byte, so the fixtures cannot drift from the protocol.
2. **Why not `parseFloat` for prices?** Binary floats cannot represent most decimal
   prices; `1.15 / 0.05` is 22.999999999999996. The text is split into digits, scaled to
   `BigInt` and required to be an exact multiple of the tick; off-grid input is refused
   with the two nearest valid prices.
3. **What breaks when JSON carries a 64-bit integer to a browser?** It becomes a double and
   silently loses precision past 2^53. The API either bounds a value or sends it as a
   string, refuses to send anything else, and the browser's parser throws instead of
   rounding. The guard caught nanosecond timestamps in development.
4. **How do you rate-limit by client IP behind a reverse proxy without letting clients
   spoof it?** Have the proxy overwrite `X-Forwarded-For`, believe the header only when the
   TCP peer is that proxy, take only the entry it wrote, and turn off the server's own
   proxy-header handling so there is one decision point. A test sends a spoofed header from
   a non-proxy and checks it is ignored.
5. **How does the UI avoid overstating a backtest?** Results are out-of-sample walk-forward
   only, costs are on by default, the first sentence says when the deflated Sharpe ratio
   (which accounts for the number of variations tried) is below 0.95, and every run,
   failed ones included, is counted on the page.
