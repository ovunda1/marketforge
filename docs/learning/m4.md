# Milestone 4: Journal and replay

Done when the determinism hash test passes: replaying the same journal gives the same
SHA-256, in the same process and in fresh processes.

## What was built

- **Session-wide order-id uniqueness**, in the book. An id is used up once its order is
  acked and stays used after the order fills or is cancelled. A rejected order never
  used its id. This closes the M2/M3 gap where a filled order's id could be reused. The
  Python reference, the generator (version 2 now reuses cancelled and rejected ids) and
  a new golden scenario (`id_reuse`) follow the same rule.
- **Injected clock**: `Clock` interface and `SimulatedClock`. A test fails if
  `engine/include` or `engine/src` read the host clock.
- **Sequencer**: assigns gapless `seq_no`s, stamps `clock.now()` and appends to the
  journal before the book sees the command (write-ahead).
- **Binary journal**: a 16-byte header, then length-prefixed little-endian records with
  `seq_no`, timestamp, type, payload and CRC32. The reader reports truncation,
  corruption, sequence gaps and timestamps going backwards, with the byte offset and
  the last good `seq_no`.
- **Snapshots**: `OrderBook::state()` / `from_state()` and a CRC-protected file format,
  written periodically during replay.
- **`mf-replay`** prints the SHA-256 of the canonical (M3) event stream, optionally
  starting from a snapshot. **`mf-journal`** converts text commands into a journal
  through the real sequencer.
- Hand-written CRC-32 and SHA-256 (no crypto dependency), checked against standard
  test vectors.
- A committed version-1 journal (`engine/tests/journal/v1.mfj`) with its expected hash.

   ordering stage, in ten lines.
3. `engine/src/journal.cpp`:
   - `encode_record`: the layout as code.
   - `JournalReader::next`: the order of checks. Length bounds come before any read.
     The CRC comes before decoding. Seq and time continuity come last.
   - `JournalWriter::write_all`: one `write(2)` per record, and why there is no fsync.
4. `engine/src/order_book.cpp`:
   - `on_new_order`: `used_ids_` replaces the old resting-only duplicate check.

   `engine/tests/replay_test.cpp` (snapshot + tail) and `tests/test_replay.py` (fresh
   processes, the driver and the Python reference).

## Design decisions

- **The journal stores inputs, not outputs.** Outputs are a pure function of the
  inputs, so storing them would be redundant and could disagree with the inputs. One
  hash over the regenerated output proves determinism.
- **Every command that gets a `seq_no` is journaled, rejects included.** A reject
  depends on book state, so it is only known after matching. Journaling only accepted
  commands would mean matching before writing, which loses write-ahead. Replay must
  reproduce every event the client saw, and gapless `seq_no`s make any gap a detectable
  error.
- **ID uniqueness lives in the book, not the sequencer.** Replay doesn't run the
  sequencer, since `seq_no`s and timestamps come from the file. A reject issued by the
  sequencer would be missing from the replayed stream. In the book, the check also
  keeps its place in the validation order, so an invalid price is still reported
  before a reused id.
- **A rejected order frees its id.** A reject means the order never existed (the M3
  rule), so it shouldn't use anything up.
- **Timestamps are journaled inputs, not re-read on replay.** A replay running at a
  different time, or speed, sees exactly the original timestamps. Non-decreasing (equal
  allowed), because several commands can share a clock tick.
- **Byte-by-byte little-endian encoding, never `memcpy` of structs.** Padding, field
  order and host endianness can't change the file. The test's expected bytes were
  worked out separately with Python `struct` and `zlib.crc32`.
- **Length prefix plus CRC per record, length checked first.** The length frames
  records and allows new types later. Checking its range before reading means a corrupt
  `0xFFFFFFFF` can't cause a 4 GB allocation. The CRC covers the length too, so a
  flipped length is caught.
- **Strict reading: any damage is an error, never a partial replay.** A torn last
  record after a crash is normal, but silently dropping it would hide lost commands.
  The reader reports it with the offset and the last good `seq_no`, and `mf-replay`
  prints no hash.
- **A snapshot holds future-relevant state, not just the visible book.** That means
  `next_trade_id`, `used_ids`, `last_seq_no`, the last timestamp and the journal offset,
  on top of the levels in FIFO order. Leaving any of them out makes the tail replay
  diverge. The snapshot + tail test catches that.
- **Deterministic snapshot bytes.** `used_ids` is a hash set, so it is sorted on write.
  Equal states give equal bytes whatever their history.
- **Snapshots are caches; the journal is the truth.** Snapshots are validated on load
  (CRC, then `from_state` consistency, then the next record must be
  `last_seq_no + 1`), written atomically via rename, and can always be rebuilt.
- **One formatting path.** `append_command_output` is shared by `mf_driver` and replay,
  so "replay hash = sha256(driver output)" holds by construction. The M3 difftest
  (driver = Python reference) therefore carries over to replay.
- **Own CRC-32 and SHA-256.** About 150 lines with standard test vectors, instead of an
  OpenSSL or zlib dependency on every machine and CI runner.

## Trade-offs and what was left out

- **Durability: no fsync.** Each record is one `write(2)` before the book sees the
  command, so the journal **survives a process crash but not an OS crash or power
  loss**: records still in the page cache are lost. Fixing that means fsync per record
  (slow) or group commit (fsync a batch, then acknowledge it). Both are left for later.
- **No torn-tail recovery.** A truncated last record is reported, not trimmed. A
  restart procedure that truncates to the last good record (and logs it) comes later.
- **`used_ids` grows for the whole session.** It is one id per accepted order, held in
  memory and in every snapshot. It will be cleared at session open when session states
  arrive (M5), bounding it to one session.
- **The book still allocates on the hot path** (now also `used_ids_`). The object pool
  is M6 work, where it can be measured.
- **Snapshots pause matching** for an O(N) copy on the matching thread. Taking them
  from a replica or a fork is not done.
- **Replay runs only as fast as possible.** Real-time and scaled replay need a host
  clock in the tool, not the engine.
- **Timestamps are not in the event stream.** The M3 format stays unchanged, so hashes
  are comparable with the driver and the reference. Execution reports will carry them
  when the gateway arrives (M10).
- **One journal per symbol, with no symbol id in the header yet.**
- A 1M-command replay takes about 6 s here with the O(N) invariant walk on after every
  command. That is not a benchmark: M6 measures with the checks off.

## Interview questions

1. **How do you prove the engine is deterministic?**
   The command journal is the only input. Replaying it produces the canonical event
   stream, and we hash it with SHA-256. The same journal replayed twice, or in two
   fresh processes, gives the same hash. A committed version-1 journal must keep
   replaying to its recorded hash, and for random 100k–1M command streams the replay
   hash equals the hash of the independent Python reference engine's output.
2. **Do you journal rejected orders? Why?**
   Yes, everything that gets a `seq_no`. Whether a command is rejected depends on book
   state, so you'd have to match before journaling, which breaks write-ahead. The
   client saw the reject, so replay must reproduce it. And with gapless `seq_no`s, a
   gap is always corruption.
3. **What happens if the process crashes mid-write?**
   The last record is torn. On read, the length prefix says how many bytes to expect,
   the file ends early, and the reader reports "truncated record at byte offset X,
   last good seq_no N". It never replays the partial record or hides it. Every earlier
   record survives a process crash, because each one went to the OS with `write` before
   the book saw it. It does not survive power loss without fsync, which is why group
   commit is the next step.
4. **What has to be in a snapshot for replay from it to match a full replay?**
   Everything the future depends on: the levels and FIFO order, partial fills, each
   order's STP mode and post-only flag, plus `next_trade_id`, the set of used order
   ids, the last `seq_no` and timestamp, and the journal offset to resume from.
   Without the used ids, a restored book would accept a duplicate id that the full
   replay rejects. The test compares the tail's stream with the full stream after the
   snapshot point, byte for byte.
5. **Why is the duplicate-id check in the book rather than the sequencer?**
   Because replay skips the sequencer: `seq_no`s and timestamps are read from the
   journal. Anything the sequencer decided wouldn't be re-decided on replay, so its
   rejects would vanish from the replayed stream. Keeping all decisions in the
   deterministic core makes the journal sufficient to reproduce them.
