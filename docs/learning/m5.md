# Milestone 5: Risk gate

Done when every reject code has a test. The main constraint was determinism:
replaying a journal must reproduce every risk reject exactly.

## What was built

- **`Engine`** (`engine.hpp`): one symbol's risk gate in front of its order book.
  Every sequenced command, live or replayed, goes through
  `Engine::process(command, timestamp)`. `replay()`, `mf_driver` and snapshots now use
  it instead of a bare `OrderBook`.
- **`RiskGate`** (`risk.hpp`): every check in the SPEC risk table, with its reason
  code. That covers `MAX_QTY`, `MAX_NOTIONAL`, `PRICE_BAND`, `POSITION_LIMIT`,
  `INSUFFICIENT_CREDIT`, `MAX_OPEN_ORDERS`, `RATE_LIMIT` (integer token bucket),
  `KILL_SWITCH` (account and global, optionally cancelling open orders) and
  `MARKET_CLOSED`. Duplicate ids stay the book's `DUPLICATE_ORDER_ID`.
- **Market-order protection:**
  - with a price band, a market order trades only up to the band edge and the rest is
    cancelled as `UNFILLED`;
  - with a band but no reference price, it is rejected;
  - for notional and credit it is valued by a read-only walk of the book.
- **Sessions:** `PRE_OPEN`, `CONTINUOUS`, `HALTED`, `CLOSED`, with a fixed transition
  table. Halted, pre-open and closed reject new orders and replaces but accept cancels.
  A new `DAY` time in force expires at the close (`CXL reason=EXPIRED`). `used_ids`
  resets at session open, keeping resting ids.
- **Admin commands** (`SetSession`, `SetInstrumentLimits`, `SetAccountLimits`,
  `KillSwitch`), journaled like orders, with `SES` / `ADM` / `AREJ` events.
- **YAML config** (`risk_config.hpp`, separate `mf_config` library on yaml-cpp 0.9.0).
  It turns a file into admin commands in a fixed order. `mf_driver --config` and
  `mf-journal --config` use it.
- **Text format:** admin lines and `T <ns>` clock lines.
- **Journal version 2** (four new record types, DAY) and **snapshot version 2** (risk
  state, time in force). Both still read version 1.
- **Sanitizers:** an ASan + UBSan CI job (ctest, then pytest against the instrumented
  tools) and `make sanitize`.
- **Test fixtures:**
  - 7 hand-derived risk golden scenarios;
  - a seeded risk-flow generator (`tests/risk_flow.py`);
  - a committed version-2 journal (`v2.mfj`, every risk reject inside) with its hash;
  - a version-1 snapshot written by the M4 build, with M4's tail hash.

## Read first

1. `docs/risk.md`: the check order table, the price band, market orders, the token
   bucket, sessions, and what the snapshot stores.
2. `engine/src/engine.cpp`, `Engine::process`: the whole pipeline in one function, in
   this order:
   - the seq_no check;
   - the gate;
   - the book (or `skip_seq_no` for a risk reject or an admin command);
   - `RiskGate::apply` over this command's events;
   - the consistency check.
3. `engine/src/risk.cpp`:
   - `check_new` / `check_replace`: the check order as code;
   - `take_token`: fixed-point refill in 128 bits;
   - `in_band` / `band_edge`: the price band, all integer;
   - `apply`: risk state from events only;
   - `from_state`: exposure rebuilt from the book.
4. `engine/src/order_book.cpp`:
   - `validate_new` / `validate_replace`: static checks the gate calls in its own
     order;
   - `sweep_notional`: the market-order walk;
   - `cancel_where`: DAY expiry and kill-switch cancels in book order.
5. Tests:
   - `engine/tests/risk_test.cpp`: one test per code, the check-order table, market
     orders, overflow and exposure;
   - `session_test.cpp`;
   - `risk_replay_test.cpp`: determinism, snapshot tails, both fixtures;
   - `tests/test_risk_replay.py`: fresh processes, YAML equivalence.

## Design decisions

- **Admin changes are journaled commands, not side-channel state.** The journal is the
  only input to replay. A limit loaded from a file, or changed through an endpoint
  without a `seq_no`, would be invisible to replay, which would then check orders
  against the wrong limits. As commands, each change sits at the exact `seq_no` where
  it took effect. The YAML file is only a way to produce those commands; the engine
  never reads it.
- **The gate sits after the sequencer, inside the deterministic core.** The sequencer
  still never rejects. A risk reject depends on state (positions, open orders, tokens)
  that only the engine has, and replay does not run the sequencer. A reject decided
  there would vanish on replay. This is the same reasoning as M4's duplicate-id check.
- **Time for the rate limiter is the journal timestamp.** It is the injected clock's
  value, stamped once by the sequencer. Replay reads it from the record, so no clock
  is read anywhere in the engine. Text files get the same time through `T` lines, so
  `mf_driver` and `mf-journal` agree; `mf-journal`'s default step changed to 0 for that.
- **Integer everything.** The token bucket counts in units of 1e-9 orders. The band
  check is `|p x den - num| x 10000 <= num x bps`, with a mid as `(bid + ask) / 2`
  (`den = 2`). Notional, exposure and refill products use `__int128`, so no input can
  overflow, which the UBSan job enforces.
- **Price-band reference: last trade, then mid, then the configured reference.** A
  trade is a real execution; one account can move a mid by posting a wide quote on a
  thin side. With no reference at all, limit orders skip the band: there is nothing to
  measure against, and `MAX_QTY` and `MAX_NOTIONAL` still apply.
- **Market orders: cap at the band edge instead of rejecting.** A market order's risk is
  its unbounded price. The cap bounds it while still filling what is reasonable. With a
  band but no reference, the order is rejected because there is nothing to cap it at.
  Without a band it is never rejected for that, so the M3 goldens did not change.
- **Market notional = a read-only walk.** It is the true maximum cost: only quantity
  that exists, skipping the account's own orders (STP can only cancel them and let the
  sweep go deeper), stopping at the band edge. It runs only when a notional or credit
  limit is set.
- **Risk state from the engine's own events.** Acks, fills, cancels of every reason, and
  replaces update positions and exposure. The same code runs live and on replay, so the
  two cannot diverge. The gate keeps its own `order_id -> {account, side, price,
  leaves}` index, because `Cancelled` and `Ack` do not carry the account.
- **Snapshots store only what the book cannot rebuild.** Open-order exposure is
  recomputed from resting orders on restore. With `MF_CHECK_INVARIANTS`, the
  incremental totals are compared with a walk of the book after every command.
- **Worst-case position, open-order-only credit.** The position check counts open orders
  on the same side, otherwise many small orders could each pass on their own. Credit
  covers open orders only. A fill moves exposure out of credit and into the position,
  which the position limit bounds.
- **A fresh engine is M4's engine.** Continuous, no limits. The differential test,
  the M3 goldens and the committed `v1.mfj` hash all pass unchanged, which proves the
  gate adds nothing when unconfigured.
- **Canonical encodings.** Unset limits are written as 0 behind a presence mask, and
  scope 0 carries account 0. Each command and each risk state has exactly one byte
  encoding, and the reader rejects anything else.

## Trade-offs and what was left out

- **Two refinements of the approved plan.**
  - *Replace check order:* a replace carries no account, so the order is found (price,
    qty, unknown order, qty too low) before its account's kill switch and bucket are
    checked. A malformed replace therefore does not use up a token.
  - *Market valuation with a band:* the walk stops at the band edge. The plan said
    "qty x far edge", but for a sell the far (lower) edge would underestimate the
    gross notional.
- **Per-symbol limits only.** Account credit and open-order counts are per account per
  symbol. A cross-symbol view needs a shared, ordered risk service. Multi-asset
  margining is a SPEC non-goal.
- **No `client_order_id`.** `order_id` is client-assigned and unique per session, which
  is stricter than the SPEC's per-account `DUPLICATE_ID`.
- **The Python reference stays book-only.** Risk is covered by unit tests, C++-only
  goldens and determinism tests, not by a second implementation.
- **Allocation.** The gate allocates on first sight of an account and per open order
  (`std::map`, `std::unordered_map`). The object pool and benchmarks are M6.
- **No opening auction.** Pre-open only rejects orders.
- **Measured along the way.** The first consistency check copied the whole
  `BookState` (including sorting `used_ids`) after every command. The 100k-command
  `mf_driver` run went from 1 s in M4 to 47 s. Walking the book in place brought it
  back to 0.9 s, and pytest went from 4 min to 10 s.
- **The sanitizer job paid for itself immediately.** UBSan flagged a signed `int`
  overflow (`i * 50'000'000`) in one of the new tests before CI ever ran.

## Interview questions

1. **How does replay reproduce a rate-limit reject without a clock?**
   The token bucket's only input is the command's timestamp. The sequencer stamped it
   from the injected clock and wrote it to the journal record. Replay passes the
   record's timestamp to the engine, so the bucket sees the same times and the same
   decisions follow. Tokens are integers (1e9 units per order) and the refill multiply
   is 128-bit, so there is no floating-point or overflow difference between machines.
   Buckets are also in snapshots, so replay from the middle agrees too.
2. **An operator changes a limit at 10:03. How does replay know?**
   The change is an admin command. It is sequenced and journaled like an order, gets a
   `seq_no` and takes effect from the next command. Replay meets it at the same point
   in the stream. A config file read at startup would not be reproducible, so the YAML
   is only converted into these commands.
3. **What does the price band compare against, and what about a market order?**
   The last trade first: it is a real execution, and a mid can be moved with one wide
   quote. If there has been no trade, it uses the mid of a two-sided book, then a
   configured reference price. It is all integer; the mid is compared as `2p` against
   `bid + ask`. A market order has no price to check, so it is capped at the band edge
   and its remainder cancelled. If a band is configured but there is no reference, it
   is rejected, because nothing would bound it.
4. **Why is the position check "worst case", and why doesn't credit include filled
   positions?**
   Without counting open orders, an account could place many orders that each pass
   and all fill together past the limit. Credit is defined over open orders (what is
   working). Once filled, the exposure is a position, and the position limit bounds
   it. The two limits split the job rather than double-counting.
5. **How do you know the risk state in a snapshot is right?**
   Most of it is not stored: exposure is rebuilt from the resting orders in the book
   section, so it cannot disagree. What is stored (positions, buckets, limits, kill
   switches, session, last trade) is validated on load. Tests restore an engine and
   check that its future events equal the original's, command for command. Snapshot
   tails replay byte-identically to the full replay of a journal containing every risk
   reject. In invariant builds, incremental exposure is checked against a walk of the
   book after every command.
