# Milestone 2: Core book

Commit `0e99b1e`. Done when unit tests pass.

## What was built

- `mf::OrderBook`: a single-symbol limit order book with price-time priority.
  Commands are `NewOrder` and `Cancel` (a `std::variant`); `process()` appends
  events to a caller-owned vector.
- Limit orders, partial fills across several levels, cancel. Trades print at the
  resting order's price.
- Events: `Ack`, `Reject`, `Fill` (maker/taker, `leaves_qty`, `cum_qty`),
  `Cancelled`, `Trade`. Every event carries the causing command's `seq_no`; a
  `Trade` and its two `Fill`s share a `trade_id`.
- Invariants: an always-on `seq_no` monotonicity check, and an O(N) consistency walk
  after every command behind `MF_CHECK_INVARIANTS` (CMake option, default ON).
- 29 GoogleTest cases, written before the implementation: matching, FIFO, cancel,
  rejects, conservation, a seeded random flow and a determinism check.

## Read first

1. `engine/include/mf/types.hpp`: `Price`/`Qty` are `int64_t`; ids and `SeqNo` are
   `uint64_t`.
2. `engine/include/mf/commands.hpp` and `engine/include/mf/events.hpp`: the
   engine's whole input and output vocabulary.
3. `engine/include/mf/order_book.hpp`: the `Order`/`Level` structs, the two
   `std::map`s and the `orders_` index. The comments explain pointer stability.
4. `engine/src/order_book.cpp`:
   - `OrderBook::process` — seq check, dispatch, invariant walk.
   - `match` — the sweep: best level first, `level.head` first, trade at
     `level.price`.
   - `append` / `unlink` — the intrusive FIFO queue.
   - `check_invariants` / `check_side` — what "consistent" means.
5. `engine/tests/order_book_test.cpp`: the behaviors, one test each.

## Design decisions

- **`std::map` per side, best price at `begin()`.** Bids use `std::greater`, asks
  `std::less`, so both sides read "best first" and `match` is written once as a
  template. O(log L) insert/erase of levels, O(1) best price. The spec says to start
  here and benchmark a flat tick-indexed array in M6.
- **Intrusive doubly linked list per level.** The `Order` *is* the list node
  (`prev`/`next`/`level` pointers), so cancel unlinks in O(1) without a second
  allocation or a search. `std::list` would need a separate node plus a stored
  iterator.
- **Cached `total_qty` and `order_count` per level.** Depth queries and later market
  data are O(1) per level; the invariant walk proves the caches match the orders.
- **`unordered_map<OrderId, Order>` owns the orders.** O(1) lookup for cancel. It is
  node-based, so element addresses survive rehashing and the intrusive pointers stay
  valid. It is never iterated to produce output, which keeps determinism intact.
- **`std::map` nodes never move**, so each order's `Level*` stays valid while other
  levels are inserted or erased.
- **Non-copyable book.** Orders point into the book's own containers; a copy would
  hold dangling pointers.
- **Events into a caller-owned vector, never cleared.** No callback indirection, the
  caller controls allocation and batching, and tests can inspect a whole command's
  output.
- **Event ordering is fixed per command:** `Ack`/`Reject`, then per match `Trade`,
  maker `Fill`, taker `Fill`. A fixed order is what makes byte-identical replay and
  line-by-line diffing (M3) possible.
- **`seq_no` check always on, O(N) walk optional.** The seq check is O(1) and replay
  correctness depends on it; the full walk is too slow for benchmarks, so M6 builds
  turn it off. Both throw `InvariantViolation`: a bug, never a normal reject.
- **Tests written first, and behaviors pinned.** M2 deliberately allowed self-trades
  and reuse of ids that are no longer resting, with tests
  (`SelfTradeCurrentlyAllowedUntilStpInM3`) so that changing them later had to be a
  visible test change.

## Trade-offs and what was left out

- **Heap allocation on the hot path.** `orders_` allocates a node per resting order
  and `std::map` per new level; the spec's pre-sized object pool is not done yet. The
  events vector can also grow. This is the main known gap against the "no heap
  allocation" convention, left for M6 where it can be measured.
- **Best bid/ask not separately cached**; `map::begin()` is already O(1).
- **No order types beyond GTC limit, no modify, no STP** (all M3).
- **Order model is minimal:** no `symbol` (one book per symbol) and no
  `client_order_id` yet.
- **No market data** (L1/L2/L3), session states or risk checks.
- Duplicate-id check covers resting orders only; session-wide uniqueness belongs to
  the sequencer (M4).

## Interview questions

1. **What data structures back the book, and what are the complexities?**
   Per side a `std::map<Price, Level>`: O(log L) to add/remove a level, O(1) best price.
   Per level an intrusive FIFO: O(1) append and unlink. A hash index from `order_id`:
   O(1) cancel. Matching is O(levels touched + orders filled).
2. **Why an intrusive list instead of `std::list` or a `std::deque`?**
   Cancel from the middle of a queue must be O(1). The order already knows its
   neighbours, so there is no search, no separate node allocation and no stored
   iterator to keep in sync.
3. **How do you know the book is consistent?**
   After every command (when enabled) `check_invariants` walks every level and order:
   links, cached totals and counts, filled + leaves = original, index membership, and
   that the book is not crossed. Any failure throws, so tests and the random flow test
   catch it at the exact command.
4. **Why does a trade print at the resting order's price?**
   The resting order set that price first; the incoming order agreed to pay up to its
   limit, so it gets price improvement. That is standard continuous-auction behavior.
5. **How is the output deterministic if you use an `unordered_map`?**
   The hash map is only used for lookup and counting. Everything that produces output
   iterates ordered structures (`std::map` levels, linked-list queues), and there is
   no clock or randomness in the engine.
