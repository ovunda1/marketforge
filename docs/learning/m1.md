  `services/{api,worker}/`, `dashboard/`, `deploy/`, `docs/` (empty dirs hold a

  `mfengine`, and a pytest job.

## Design decisions

- **One engine library, linked everywhere.** `mf_engine` is a library, not an
  executable, so tests, the driver (M3), the Python extension and later the gateway
  and backtest worker all link the same matching code. That is the spec's core
  promise: live and simulated trading share one engine.
- **Position-independent static library.** PIC lets the same static library be linked
  into the shared Python extension without a second build.
- **Dependencies via `FetchContent` at pinned versions** (GoogleTest 1.15.2,
  pybind11 3.0.1). No system packages to install; every machine and CI runner builds
  the same versions.
- **Bindings off by default.** Most sessions only touch C++; requiring a Python dev
  install for every `make build` would slow the loop. CI still builds and imports the
  stub, so it cannot rot.
- **Python always in `.venv` with 3.12.** `make venv` prefers a uv-managed 3.12
  because Homebrew's python@3.12 has a broken `pyexpat` on macOS 26.
- **gcc and clang in CI.** The two compilers disagree on warnings and on some
  undefined-behavior consequences; catching that early is cheaper than at M6.
- **Conventions written down before any engine code:** integer ticks, no wall clock,
  determinism, tests per feature, no allocation or locks in the hot path. Every later
  milestone is checked against them.
- **`RelWithDebInfo` default build type.** Optimized enough to be realistic, with
  symbols for debugging.

## Trade-offs and what was left out

- Placeholder tests only; they prove the pipeline, not the code.
- No packaging: scikit-build-core arrives in M7, so `mfengine` is a bare CMake target.
- No `bench`, `lint`, `fmt`, `up`, `down`, `replay`, `demo` targets yet; no sanitizer,
  clang-tidy, ruff or mypy jobs (the spec wants them; they come later).
- `FetchContent` downloads on every fresh configure: simple, at the cost of network
  access and a slower first build.

## Interview questions

1. **Why is the engine a library instead of an executable?**
   So the exact same matching code runs in unit tests, the differential-test driver,
   the Python backtester and the live gateway. Any divergence between "backtest" and
   "live" would make backtest results meaningless.
2. **Why integer prices instead of `double`?**
   Floating point makes equality and ordering inexact and can differ across
   compilers/flags. A price level is a map key; `100.1 + 0.2` not equalling `100.3`
   would split or lose levels. Integer ticks are exact and portable.
3. **Why ban the wall clock in the engine?**
   Output must depend only on the input command stream so replays are byte-identical.
   Time is a sequencer-assigned `seq_no`; real timestamps come from an injected clock
   that replay can simulate.
4. **Why test with both gcc and clang?**
   Different warnings, different optimizers, different exploitation of undefined
   behavior. Code that only works on one compiler usually has a latent bug.
5. **How do you keep CI and local builds consistent?**
   Pinned dependency versions via `FetchContent`, a pinned Python minor version, and
   the same CMake commands in the Makefile and the workflow.
