# M10: Services

## What was built

The engine became an exchange you can talk to: a REST and WebSocket gateway, PostgreSQL
and Redis, a backtest worker, all started by `make up`. The shape follows one rule:
**exactly one process owns the engines and journals**, and everything else is derived
from the journal.

- **Matcher** (`services/matcher/`): the single writer. One `Engine`, journal, intake log
  and market-data feed per symbol. It reads gateway requests from a Redis stream in
  batches; each batch is one group commit (intake log, then journal, both fsynced); then
  it publishes replies, execution reports and market data. On restart it rebuilds each
  symbol from its newest snapshot plus the journal tail.
- **Gateway** (`services/api/`): FastAPI, several worker processes, no engine. Order
  entry and admin commands go to the matcher; reads come from Postgres and the Redis
  book cache; WebSocket clients are fed from Redis pub/sub through a per-worker fan-out
  hub with bounded queues. API keys are stored as SHA-256 hashes.
- **Projector** (`services/projector/`): replays the journals through its own engine and
  writes Postgres in transactional batches, each moving a per-symbol cursor. Rebuildable
  from scratch (`make projection-rebuild`); `python -m services.projector verify`
  compares Postgres with a fresh replay.
- **Postgres schema** (`services/db/`): SQLAlchemy 2.0 Core tables, one Alembic revision,
  checked against the models (`alembic check`) by the round-trip test.
- **Backtest worker** (`services/worker/tasks.py`): arq jobs running `research.runs.run`
  (now with a progress hook that cannot change outputs), results to Postgres, progress
  and equity over `/ws/backtests/{id}`.
- **Engine changes**: `JournalWriter::resume` (continue an existing journal, trimming a
  torn final record) and `JournalWriter::sync` (fdatasync), with bindings. A gcc-only
  compile error in the bindings (a structured binding inside a template parsed as a
  dependent name) surfaced in the Linux image build and was fixed.
- **Deploy** (`deploy/`): a multi-stage Dockerfile (wheel built with scikit-build-core,
  Release, invariant walk off; slim runtime), `docker-compose.yml`, a test override, and
  `.env.example`. CI gained a job that builds the images and runs the API suite against
  the stack.

Reference: `docs/services.md` (processes, configuration, endpoints, channels).

## Design decisions

**One matcher process, not an engine per API worker.** The engine is single-threaded per
symbol and the journal is a single ordered log; two processes appending to it would
need a distributed sequencer. So API workers are stateless forwarders and scale out; the
matcher is the one place where order is decided. SPEC.md originally had the engine
embedded in the gateway; it now describes the separate process. Enforced three ways:
compose runs one replica, the matcher takes an exclusive `flock` on its data directory,
and an import test fails if `services.api` ever loads `mfengine` (another one fails if
the matcher loads a database driver).

**Commands travel over a Redis Stream.** Each gateway worker XADDs to `mf:cmd` with a
request id, its own reply stream and a deadline; one task per worker reads its reply
stream and resolves a future per request id. Redis was already required for fan-out,
and a stream keeps queuing while the matcher restarts. A direct socket would save a hop
but needs its own reconnect and queueing logic. The matcher reads with
`XREADGROUP ... NOACK`: at most once. A request lost between the read and the journal
write is never acknowledged, so the client times out (504: "outcome unknown") and
retries with the same key.

**Idempotency belongs to the single writer.** `client_order_id` (required) and an
optional `Idempotency-Key` for cancel and replace are checked by the matcher before a
seq_no is assigned: same key and payload returns the original order (`replayed`), same
key with a different payload is a 409. It cannot live in Postgres, which lags, or in the
gateway, which has several processes. The journal's binary format has no field for the
key, so the matcher keeps the **intake log**: one JSON line per sequenced command with
the request id, key, payload hash and assigned order id. Restart rebuilds the key map
and the order-id-to-symbol registry from it, and the projector reads `client_order_id`
from it.

**Durability: intake, then journal, then reply (group commit).** Per batch:

1. write every intake entry, fsync each touched intake log;
2. for each command: append the journal record, then run the engine;
3. fsync each touched journal;
4. only now return, so replies, executions and market data go out.

The review of the plan caught the important part: if intake and journal were only
fsynced in that order *after* both writes, an OS crash could still keep a journal record
whose intake entry was lost. The kernel writes dirty pages back whenever it likes, so a
journal page can reach the disk before the intake fsync. A retry would then create a
duplicate order. Syncing the intake log *before the first journal write* makes that
impossible. The crash tests model it adversarially: unsynced journal data survives,
unsynced intake data is lost. A mutation check (moving the intake fsync after the
journal writes) fails six of them, including the dedicated power-loss test. Entries
beyond the journal (a crash between phases 1 and 2) are orphans: never sequenced,
removed at restart, and their order ids are reused.

One fsync per file per batch, not per command: under load the batch grows and the cost
per command falls, which is the point of group commit.

**What the guarantee covers.** On a Linux host, an acknowledged command survives power
loss. On macOS, `fsync` does not flush the drive's write cache (`F_FULLFSYNC` would),
so a power cut can lose synced data. Docker Desktop runs containers in a Linux VM whose
disk is a file on the host, so an fsync inside a container reaches the VM's disk, and
what reaches the physical disk depends on the VM and the host. The power-loss guarantee
is for Docker on Linux. A process crash (kill -9, segfault) is covered everywhere: data
in the page cache survives.

**Restart = newest usable snapshot + journal tail.** Per symbol: `JournalWriter::resume`
validates the journal and cuts a torn final record (write-ahead means it was never
processed or acknowledged). Any other damage stops the matcher for an operator. Then
orphan intake entries are dropped, and a journal record without an intake entry is a
hard error (`IntakeMismatch`). The newest snapshot that decodes and is not beyond the
journal is loaded; a damaged one falls back to an older one or a full replay. The tail
is replayed and a new epoch starts. The matcher writes a snapshot every N commands and
on SIGTERM; snapshots are only a cache.

**The projection is derived from the journal, not from Redis.** The projector tails each
journal file and regenerates the events with its own engine; determinism makes them
identical to the matcher's. Each batch is one transaction that applies row operations
and moves `projection_cursor` *only if it is still where the batch started*
(`SELECT ... FOR UPDATE`, then compare). So a batch applies exactly once, even when the
projector crashes after committing or a second projector runs. If the cursor is ahead of
the journal (records lost in an OS crash that the projector had already read), that
symbol is rebuilt. Reads that must see a write pass the `seq_no` the write returned as
`min_seq_no`, and the gateway waits for the cursor.

**Market data: snapshot, numbered deltas, epochs.** After each batch the matcher diffs
the top `depth` levels per side against what it last published and sends the changed
levels, trades and L1 with `md_seq` +1. The book snapshot is SET in Redis in the same
MULTI/EXEC as the PUBLISH, so a snapshot and the updates after it always line up. A
client applies updates while `md_seq` is contiguous within an `epoch`; a gap or a new
epoch (each matcher start) means a new snapshot. Updates already contained in a
snapshot are skipped.

**A slow client costs only itself.** The matcher publishes to Redis and never knows
about clients. Each gateway worker has one subscription and a `Hub` whose `publish` is
synchronous: it appends to each subscriber's bounded queue and never awaits a socket.
On overflow the queue is emptied and the client is sent `resnapshot` plus a fresh
snapshot. Repeated overflows, or a send blocked past the send timeout, close it with
4008. If a whole gateway worker falls behind, Redis cuts its subscription
(`client-output-buffer-limit pubsub`) and its clients resnapshot. The compose test
freezes a client's container with `docker pause` while 4000 orders flow: the frozen
client is closed with 4008 and recovers by resnapshotting; a fast client on the same
symbol sees every update in order. Getting that test to fail without the policy showed
something worth knowing. WebSocket permessage-deflate shrank these similar JSON updates
so much that a frozen client's backlog fit in the socket buffers. Compression is now
off: it costs the server a separate compression stream per client, and it hides lag.

**API keys.** `mf_<8 hex prefix>_<32 random bytes>`. The prefix finds the row, and the
database keeps the SHA-256 of the whole key. A fast hash is right here because the key
has 256 bits of entropy; a password chosen by a person would need a slow, salted hash.
Constant-time compare; the key is printed once by `services.api.accounts create`.

**Secrets.** The DB password and Tiingo key come from the environment, which compose
fills from a git-ignored `.env` (`${POSTGRES_PASSWORD:?}`: compose refuses to start
without it). `.dockerignore` keeps `.env` out of the build context, and no `ARG`/`ENV`
carries a secret. Tests lint the deploy files, check `.env` is ignored, and in the
compose suite search `docker history`/`inspect` of every image for the real password.
Only the worker receives `TIINGO_API_KEY`.

**The wall clock lives in the services layer.** The matcher stamps commands with
`time.time_ns()`, made non-decreasing per symbol; the engine still only sees journal
timestamps, so replay never reads a clock.

**Backtests are retried, not resumed.** A SIGKILLed worker leaves its arq job queued;
arq reruns it once the job's in-progress lock expires (job timeout + 10 s). Runs are
deterministic and every write is keyed by the run id, so the retry rewrites the same
rows (`attempts` counts them). A run that fails on its own (bad config) is marked failed
and not retried.

## Test strategy

- **Offline, in `make test`** (no Docker): the matcher against temp dirs and a fake
  clock, including the crash matrix (5 crash points x process crash / power loss keeping
  the journal / power loss losing unsynced data, then retries with the same keys must
  reproduce an uninterrupted run's books and positions). Also the intake log, market
  data (snapshot + deltas = engine depth after every batch, seeded random flows), the
  fan-out hub, the projection (hand-derived session; incremental in random chunks ==
  one-shot rebuild; stale cursor refused), the gateway with fake dependencies through
  httpx's ASGI transport, auth, import boundaries and secret lint. C++: resume at every
  tear point, refusal of other damage, resumed == uninterrupted bytes.
- **`make test-services`**: a fresh compose project (`mf-test`) with a test override,
  the suite over real HTTP and WebSocket, then torn down. It covers kill -9 of the
  matcher under load followed by retries with the same keys; kill -9 of the projector and
  of the backtest worker; the frozen client; idempotency under 20 concurrent duplicates;
  500 orders through both API workers; and `verify` (Postgres == fresh replay of every
  journal) after each. A failing test attaches the compose logs. CI runs the same target.
- One early full run failed five compose tests on a stack reused from manual runs. The
  log was lost, and five later runs (three fresh, two reusing the stack) all passed. The
  target now always starts from an empty project and keeps logs on failure.

## Trade-offs and what was left out

- **No matcher failover.** One writer means a restart is downtime: requests queue in the
  stream and expire after their deadline. Hot standby replaying the journal is the
  standard next step.
- **Order entry over WebSocket**: not built (REST only); the SPEC lists both.
- **Cross-symbol risk**: limits stay per symbol (one engine per symbol, docs/risk.md).
- **Unbounded in-memory registries**: the matcher keeps every order id and idempotency
  key since the journal began. Session rollover with journal rotation would bound both.
- **Journal rotation and snapshot pruning by age**: one journal per symbol, forever.
- **The power-loss guarantee is Linux-only** (see above); no `F_FULLFSYNC` on macOS.
- **Execution reports have no replay channel**: after a drop, the client resyncs over
  REST; per-account sequence numbers for executions are not implemented.
- **Rate limiting** at the gateway is a fixed one-second window in Redis; the engine's
  token bucket remains the authoritative one.
- **Prometheus and Grafana** are not in the compose file; `/metrics` and the matcher's
  `:9101/metrics` are ready for them.
- **The dashboard** is M11.
- **No benchmarks**: `make gateway-smoke` prints REST round-trip and WebSocket timing
  for a sanity check. On Docker Desktop the matcher's batches (both fsyncs included)
  were a small fraction of the round trip; the gateway and Docker's networking dominate.

## Interview questions

1. **Why exactly one matcher, and how do you guarantee it?** The journal is one ordered
   log per symbol and the engine is single-threaded; two writers would need distributed
   sequencing. Gateway workers are stateless and scale; the matcher decides order.
   Guaranteed by one replica, an exclusive `flock` on the data directory, and tests that
   fail if the API imports the engine.
2. **A client gets a timeout on POST /orders. What happened and what should it do?** The
   outcome is unknown: the request may have been journaled just before its deadline, or
   never sequenced. Retry with the same `client_order_id`: the matcher returns the
   original order if it exists, otherwise executes it now. That works across matcher
   crashes because keys are rebuilt from the intake log.
3. **Why fsync the intake log before writing the journal, not just before syncing it?**
   The kernel may write a dirty journal page back at any time. If the journal record
   reaches the disk and the intake entry does not, an OS crash leaves an order without
   its `client_order_id`, and a retry duplicates it. Syncing intake first means any
   journal record on disk has a durable intake entry; extra intake entries are harmless
   orphans.
4. **How does Postgres stay consistent with the journal if the projector dies
   mid-write?** Each batch is one transaction that also moves a per-symbol cursor, and
   only if the cursor is where the batch started. A crash before commit applies nothing;
   after commit the cursor has moved, so the restarted projector continues after it. The
   projection is a pure function of the journal, and `verify` checks that.
5. **What happens when a WebSocket client stops reading?** Its bounded queue in the
   gateway overflows; the gateway drops the backlog and sends a fresh snapshot, and after
   repeated overflows (or a send blocked past a timeout) closes it with 4008. The matcher
   only publishes to Redis and never waits on clients; Redis disconnects a gateway worker
   that falls too far behind, and its clients resnapshot.
