## Workloads

Both workloads are generated by `bench/lib/workload.cpp` from seed
20261021 (generator version
1) and run through one `Engine`: the risk gate
with every limit configured and generous (so every check runs and almost every order
passes), in front of the order book. The flow is cancel-heavy, like real order flow, and
the generator picks cancels and replaces from orders that are really resting.

- **narrow**: a fixed mid and limit prices within a few ticks of it: few, deep levels.
  Most orders resting at once: 1,001 (narrow workload).
- **wide**: the mid drifts, prices spread over thousands of ticks (log-uniform distance
  from the mid) and one order in a hundred rests far away: many shallow levels. Most
  orders resting at once: 3,989 (wide workload).

Each repetition replays 5,000,000 commands on a fresh engine; the first
500,000 of each are processed but not measured (cold caches,
first-touch page faults, clock ramp-up, the book filling to its steady size). Each
profile's event stream is checked against the SHA-256 pinned in
`bench/expected_digests.json` before any number is written.

**Reading the low percentiles.** The clock is `std::chrono::steady_clock`. On this machine
one read costs 11.5 ns and the clock moves in steps of
41 ns: two back-to-back reads return the same value
73% of the time. A command shorter than one step
reads as zero or one step, so p50 and p90 are quantised to that step and each sample
includes about one clock read. The per-command mean, less one read, differs from the batch
mean by -23.9% (narrow workload) and
-21.3% (wide workload): it comes out lower,
not higher. A clock read does not stop the processor, so part of one command's work
overlaps the reads around it and is counted in no sample. Read the histogram for the shape
of the distribution and its tail, and the batch figure (throughput) for the mean.

- `Add*`, `Cancel*`, `Replace*` and `Match*` drive the `OrderBook` alone.
- `RiskCheck` is `RiskGate::check_new` with every limit set, against `RiskCheckNoLimits`.
- `EngineAdd` is the same passive add as `AddExistingLevel` through the whole `Engine`
  (gate, book and the risk update from the events). On this build it measures *below*
  `AddExistingLevel`, although it does strictly more work, repeatably, and this is not
  explained (code layout and alignment effects are the usual suspects; Apple Silicon's
  performance counters are not available to confirm it). So the pair does not price the
  gate. `RiskCheck` against `RiskCheckNoLimits` prices the checks; the end-to-end effect
  of the gate's account lookups is opt-7 in `OPTIMIZATIONS.md`.

## Method

- Release build, `-DMF_CHECK_INVARIANTS=OFF`; the same suite and the long differential
  test pass on it (`make gate`).
- The thread asks for the `USER_INTERACTIVE` QoS class, which steers macOS towards a
  performance core (there is no API to pin a thread on Apple Silicon). A fixed integer
  loop runs before and after every repetition; if the two disagree, or either is slower
  than the session's best, by more than the tolerance in the JSON, the core changed speed
  (efficiency core, throttling) and the repetition is run again.
- `make bench` refuses to measure on battery or in Low Power Mode.
